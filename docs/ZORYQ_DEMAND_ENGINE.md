# ZORYQ Demand & Value Engine

ZORYQ should earn demand before it earns a token thesis.

The operating sequence is:

`problem -> useful product -> repeated use -> verified economic activity -> retention -> network effects -> value capture -> token, only if necessary`

A token is not the product and must not be used to manufacture apparent traction.

## North-star metric

**Verified External Economic Actions (VEEA)**

Count only actions attributable to an independently controlled participant that can be evidenced by reproducible artifacts or onchain records, such as:

- an external developer deploying or integrating a ZORYQ application;
- an independent user creating or operating an Autonomous Company;
- an independent payer/customer funding a task or service;
- an independent worker/agent completing a task and receiving a verified settlement;
- an independent node/operator contributing network operation;
- an external application generating verifiable recurring activity.

Project-controlled wallets, project CI, founder/operator machines and circular/self-interactions must be reported separately and never counted as external demand.

## Product funnel

Primary product funnel:

`Visitor -> Useful Product -> Wallet/Testnet Interaction -> Repeated Use -> Paid/Economic Action -> Referral -> Builder`

Developer funnel:

`Discovery -> Docs -> Faucet -> First Transaction -> First Contract -> First Application -> Contribution -> Ecosystem Project`

Autonomous Company funnel:

`Goal -> Company -> Plan -> Agents -> Tasks -> Hire -> Simulate -> Authorize -> Execute -> Pay/Receive -> Verify -> Reputation -> Proof Pack -> Repeat`

## Product-market-fit gates

- **PMF-0 — Works:** a clean user/developer can reproduce the intended product path.
- **PMF-1 — External use:** at least 10 independently controlled users complete the path.
- **PMF-2 — Repeat use:** external users return without project-operated transactions pretending to be usage.
- **PMF-3 — Economic use:** independent users voluntarily create verified economic actions.
- **PMF-4 — Developer pull:** independent developers build applications or integrations without being implementation proxies for the core team.
- **PMF-5 — Ecosystem pull:** third-party projects/users create activity that continues without direct founder intervention.

These are progressive evidence gates, not marketing labels.

## Demand scoreboard

Track separately, with evidence and time window:

- unique independent users;
- returning independent users;
- independent developers;
- independent contributors;
- independent node operators;
- first transactions;
- first contracts;
- first applications;
- Autonomous Companies created;
- externally initiated tasks;
- externally funded tasks;
- verified outgoing settlements;
- verified incoming settlements;
- verified external economic actions (VEEA);
- applications used more than once;
- external integrations;
- failures during onboarding and reproduction.

Never merge controlled/internal/test activity into external metrics.

## Demand experiments

Every growth or product experiment must state:

1. user/problem hypothesis;
2. smallest product change or offer;
3. target funnel stage;
4. success metric;
5. evidence source;
6. time/effort budget;
7. stop condition;
8. result and next decision.

Rank experiments with:

`Impact × Confidence ÷ Effort`

Prefer product improvements that remove friction from developer or user activation over vanity impressions.

## Token gate

Do not recommend a ZORYQ TGE merely because a blockchain exists.

Before a token recommendation, require evidence that the token performs a function that stablecoins or ETH cannot replace without materially weakening the system. Candidate functions may include:

- economic security/staking;
- validator participation and slashing;
- agent/service collateral;
- resource pricing;
- protocol fee settlement;
- reputation bonding;
- governance where governance is genuinely required;
- scarce network resources.

A credible token thesis must answer:

1. Why must demand for the product create demand for the token?
2. What prevents token demand from being purely speculative?
3. What supply/unlock/emission policy avoids overwhelming organic demand?
4. What happens if users prefer USDC/ETH instead?
5. Which independently measured usage metric feeds the value-capture model?

If these questions do not have evidence-backed answers, the correct action is to improve product demand rather than launch the token.

## Value-capture model

When token design becomes justified, model explicitly:

`Network Usage -> Protocol Fees / Required Economic Security -> Token Demand -> Supply Dynamics -> Value Capture`

Publish bear/base/bull adoption assumptions separately from facts. Never promise price appreciation or comparison outperformance versus Bitcoin or another asset.

## Current priority rule

Until external demand materially improves, prioritize in this order:

1. reproducible developer onboarding;
2. useful application completion;
3. independent Autonomous Company reproduction;
4. independently controlled economic counterparties;
5. repeated usage and retention;
6. independent contributors/operators;
7. value-capture research;
8. token design/TGE.

## Truth states

Use these states consistently:

- 🔴 does not exist;
- 🟠 prototype;
- 🟡 works internally;
- 🟢 verified/reproducible;
- 🔵 independently reproduced;
- 🟣 production use with independent recurring demand.

Green CI alone is not product-market fit. Operator-controlled economic activity is not external demand. Testnet activity is not revenue.

## Execution loop

For every operating cycle:

1. inspect verified evidence;
2. identify the highest funnel bottleneck;
3. rank executable actions by Impact × Confidence ÷ Effort;
4. execute the highest-value safe action available;
5. test or obtain public evidence;
6. record failure as evidence when an action fails;
7. avoid repeating an action without a changed hypothesis;
8. update the next bottleneck.

The long-term goal is not to launch a token. It is to build a useful, defensible digital economy that has a reason to need one.
