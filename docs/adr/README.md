# Architecture Decision Records

ZORYQ uses Architecture Decision Records (ADRs) for durable technical decisions that materially affect architecture, security, compatibility, performance or operations.

## When to create an ADR

Create an ADR when a change selects among meaningful alternatives or introduces a decision that future contributors will need to understand.

## Required structure

Each ADR should contain:

1. **Status** — Proposed, Accepted, Superseded or Rejected.
2. **Context** — why the decision is needed.
3. **Problem** — the concrete engineering problem.
4. **Options considered** — credible alternatives.
5. **Decision** — what was selected.
6. **Rationale** — why it was selected.
7. **Trade-offs** — what is lost or made harder.
8. **Security implications**.
9. **Performance implications**.
10. **Compatibility and migration implications**.
11. **Evidence / tests** — links when available.

## Naming

Use sequential names such as:

`ADR-001-execution-model.md`

Do not create placeholder ADRs for decisions that have not actually been made.
