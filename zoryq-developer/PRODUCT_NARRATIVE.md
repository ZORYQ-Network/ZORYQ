# ZORYQ Product Narrative

## One sentence
ZORYQ is an experimental agent-native EVM network where human and software-agent builders can move from intent to verifiable onchain product, while project identity, activity and reputation remain machine-readable.

## The problem
EVM execution is standardized, but the builder experience around autonomous software is fragmented. Agents need explicit context and signing boundaries. Projects need canonical identity. Ecosystems need attribution based on evidence rather than vanity metrics. Builders need useful primitives and a short path from experiment to verified deployment.

## The product system
ZORYQ is one loop, not a collection of unrelated features:

Discover → Fund → Build → Simulate → Sign → Verify → Register → Measure → Reputation.

### Execution
Standard EVM tooling and wallets. Chain ID 5919065.

### Agent layer
Machine-readable chain context and action schemas. State-changing actions must preserve explicit wallet authorization.

### Embedded primitives
Live testnet DEX, Lending, Stake and zUSD let builders compose rather than start with an empty chain.

### Project identity
The live Project Registry anchors builder-owned project identity, manifest pointers and content hashes.

### Intelligence
Project Intelligence and Builder Reputation are designed to derive useful signals from verifiable activity while separating internal/self activity from external adoption.

### Evidence
Explorer receipts, bytecode, protocol events, registry records and machine-readable network maturity are the source of truth.

## Why now
AI agents are becoming software actors, while programmable money and onchain execution provide a public settlement surface. ZORYQ tests what the developer platform should look like when both humans and agents are first-class builders.

## What ZORYQ is not claiming
- not mainnet
- not decentralized today
- no independent validator set today
- no audit claim unless an audit exists
- no monetary value for test ZQ or zUSD
- internal Treasury activity is not external traction
- Genesis finalized-onchain score is not live today

## The wedge
Do not compete on generic TPS slogans. Compete on time from idea to safe, inspectable, attributable onchain software.

The defensible direction is the combination of:
1. agent-readable execution context;
2. explicit signing/simulation boundaries;
3. builder-owned project identity;
4. verifiable project intelligence;
5. builder reputation derived from evidence;
6. useful embedded protocol primitives;
7. transparent network maturity.

## Developer promise
A developer should be able to understand the thesis in 60 seconds, make an RPC call in 2 minutes, deploy in under 5 minutes, compose with a live primitive, register the project and share a verifiable artifact without asking permission.

## Investor / partner proof hierarchy
1. Live network and RPC.
2. Live contract bytecode and transactions.
3. Reproducible developer path.
4. Independent builders and projects.
5. Repeated external usage.
6. Independent node operators and stronger network maturity.
7. Sustainable economic activity.

Never reverse this hierarchy with marketing claims.

## Design rule
Every new surface must answer at least one of four questions:
- Does it shorten builder time-to-first-proof?
- Does it make agent execution safer or more legible?
- Does it create stronger verifiable attribution?
- Does it increase credible external adoption or network maturity?

If not, it is probably not a priority.
