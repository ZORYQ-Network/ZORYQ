ZORYQ DEVELOPERS

Build verifiable on-chain products.

ZORYQ is an EVM-compatible public testnet being developed as a builder platform for humans and AI agents. The design goal is to reduce friction from idea to deployment while keeping network status, transaction intent and project activity explicit and verifiable.

Testnet status: ZORYQ is currently a centralized testing environment. ZQ, zUSD and Testnet points have no monetary value.

Faucet

The public faucet provides test ZQ for gas and testnet activity. Availability, eligibility gates and cooldowns are enforced by the current backend configuration.

POST /faucet

JSON-RPC

The public gateway targets standard Ethereum JSON-RPC compatibility while blocking administrative namespaces such as anvil_*, hardhat_*, evm_* and debug_*.

curl -X POST https://zoryq-evm-node-live-production.up.railway.app/rpc \
-H 'content-type: application/json' \
--data '{"jsonrpc":"2.0","id":1,"method":"eth_chainId","params":[]}'

Common methods include eth_chainId, net_version, eth_blockNumber, eth_getBalance, eth_getCode, eth_call, eth_estimateGas, eth_sendRawTransaction, eth_getTransactionReceipt and eth_getLogs.

Contracts and canonicality

ZORYQ supports Solidity/EVM contracts and standard tooling such as Foundry, Hardhat, ethers and viem. Public developer metadata distinguishes deployed contracts from source-only components.

zUSD canonicality warning: project history contains more than one zUSD address. New DEX v1 or Lending deployment must not claim a canonical zUSD until the live Swap Lab token address and deployed bytecode are reconciled on-chain.

DEX v1, Lending and Project Registry currently exist at source level and must not be represented as deployed until a successful transaction receipt, bytecode and intended configuration are verified.

AI-agent development

ZORYQ publishes machine-readable context for coding agents and wallets. The intended agent flow is: read network metadata → identify target → preview transaction → simulate with eth_call → estimate gas → require explicit wallet confirmation → broadcast → verify receipt → link Explorer evidence.

Agent discovery surfaces include /llms.txt, /.well-known/zoryq-agent.json, /agent/action-schema.json, /agent/project-schema.json and the Builder Reputation methodology endpoint.

ZORYQ Actions

ZORYQ Actions are structured manifests for previewable testnet actions. They describe chain, target contract, method, value, parameters, expected result and safety requirements before a wallet signs.

An action manifest never replaces wallet consent. State-changing transactions require explicit confirmation by the user's wallet.

Genesis Score

Genesis currently separates pending score, on-chain verified activity, externally verified identity and self-attested social activity. These categories are intentionally not collapsed into a single finalized claim.

pendingScoreTotal recorded Testnet participation before finalization.
verifiedOnchainScoreActions whose transaction evidence has been checked on ZORYQ.
verifiedExternalScoreExternally verified evidence such as supported identity checks.
socialPendingScoreSelf-attested social actions pending stronger verification.
finalizedOnchainScoreCurrently 0 — on-chain finalization is not live.

The Reward Registry must not be described as the current finalized source of truth while finalization is not implemented.

Project Intelligence

The Project Registry, project manifests and Builder Reputation methodology are being developed to connect projects to their declared contracts and then measure verifiable usage: unique external wallets, returning users, successful interactions, native-protocol integration, reliability and integrity flags.

No project currently has a verified live Builder Reputation score. The scoring engine exists, but a valid public score requires the Project Intelligence indexer to supply verified, anti-gaming-filtered evidence.

Security and network maturity

ZORYQ EVM Testnet is currently a centralized public testing environment, not a decentralized production Mainnet. The largest infrastructure gap remains independently operated multi-node consensus and failure testing.

Public RPC administrative namespaces are blocked. Wallet seeds/private keys must never be committed or uploaded. Canonical contract addresses require on-chain verification. Decentralization, production-readiness, finalized score and audited-protocol claims must only be made after the corresponding implementation and evidence exist.
